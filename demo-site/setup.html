Setup & Connections

What a system like this is actually plugged into, what each piece costs, and the order to wire it up. Written for whoever builds the real thing.

The short version. A system like this is one small web app plus a database, and then a series of connections to services the business already pays for. The app itself is the easy part. The value — and most of the work — is in the connections: the accounting system, the file storage, the email. Get the database and hosting up first; add connections one at a time, in the order below. Nothing here needs a server you maintain.

The two things you need before anything else

ServiceWhat it doesCostNotes
Supabase required The database. Every job, client, invoice, inventory item and history record lives here. Also handles file storage for photos and uploads. Free tier is real; $25/mo per project once you outgrow it Postgres under the hood, so nothing is proprietary — the data can be exported or moved out at any time.
Vercel required Hosting. Deploys the app automatically every time the code changes, runs the server-side functions, handles SSL and the custom domain. Free tier works to start; $20/user/mo (Pro) for real use Pro matters once you have background jobs and more than a handful of server functions.

With just those two, you have a working private app: log in, add jobs, track inventory, see totals. Everything below is a connection to something outside.

Sign-in

ServiceWhat it doesCostNotes
Clerk required Staff sign-in. Handles passwords, Google sign-in, sessions and account recovery so you never store a password yourself. Free to ~10,000 users Room 117 restricts access by email domain — anyone with a company address is staff, everyone else is refused. Simple and it has never needed maintenance.
Worth knowing early. Customers should not go through the same sign-in as staff. Room 117 learned this: clients get in by a link emailed to them, a 6-digit code, or a password they set themselves — no account to create, and they never touch the staff system. Deciding this up front saves rebuilding it later.

The money connection

ServiceWhat it doesCostNotes
QuickBooks Online Resound RM117 Two-way. The app creates customers and invoices in QuickBooks; when an invoice gets paid, the payment flows back into the app automatically. Also feeds the profit-and-loss and receivables screens. Your existing QuickBooks subscription — the API is free Accounting stays the system of record. The app is a nicer front end, never a second ledger.
The one rule that makes this work. Every job has an ID, and that exact ID must be the customer name in QuickBooks — character for character. That single convention is what lets a payment recorded in QuickBooks find its way back to the right job with no manual matching. It sounds trivial. It is the thing most likely to break, so build the rename tool that keeps both sides in step from day one, rather than fixing collisions by hand later.

What it costs to run

Realistically, for a small business running this for real:

  • Starting out: $0–25/month. Free tiers cover a single-user app with modest data.
  • A real team using it daily: roughly $45–90/month — database, hosting, and the odd API call. Sign-in is free at this size.
  • Already-paid-for: QuickBooks, Google Workspace and Slack are things the business already has. Connecting them costs nothing extra.

The recurring cost is small. The cost is the build.

The order to do it in

  1. Database first. Create the Supabase project and design the tables. Everything else hangs off this, and changing it later is the expensive kind of change.
  2. Get it deployed on day one. Connect the code to Vercel immediately, even with nothing in it. Every change should go live automatically from the start — batching that up is how projects stall.
  3. Add sign-in. Clerk, restricted to your company's email domain. Now it's private and you can put real data in.
  4. Build the core screens with no outside connections. Jobs, clients, inventory. Prove the workflow matches how the business actually runs before wiring anything external.
  5. Connect accounting. QuickBooks, read-only at first — pull the invoice list in and check it matches. Only then let the app write.
  6. Connect files and email. Drive and Gmail, once people are relying on the core.
  7. Everything else, one at a time. AI, Slack, e-signature, QR. Each is a self-contained addition, and each should be able to fail without taking the app down with it.
The one habit worth copying. Every connection above can fail — a token expires, a service has an outage, someone revokes access. In this system each one is wrapped so that when it fails, that panel says so and the rest of the app keeps working. A dashboard that goes blank because QuickBooks is briefly down is a system people stop trusting, and they only need to see it once.

Configuration, concretely

These are the environment variables the real system reads. They live in the hosting platform's settings, never in the code itself.

# Database — required
SUPABASE_URL=
SUPABASE_SERVICE_KEY=

# Sign-in — required
CLERK_SECRET_KEY=
VITE_CLERK_PUBLISHABLE_KEY=

# Accounting
QBO_CLIENT_ID=
QBO_CLIENT_SECRET=
QBO_REALM_ID=

# Google — files, mail, calendar
GOOGLE_SERVICE_ACCOUNT_EMAIL=
GOOGLE_PRIVATE_KEY=
COMPANY_CALENDAR_ID=

# Automated email
RESEND_API_KEY=

# AI features
ANTHROPIC_API_KEY=

# Slack (Resound)
SLACK_BOT_TOKEN=
SLACK_SIGNING_SECRET=
Two things not to get wrong. The service key above bypasses every permission rule in the database — it belongs on the server only, never in anything the browser downloads. And permissions must be enforced on the server, not by hiding buttons in the interface: a hidden button is not a permission.

About these demos

Both demos on this site are deliberately built the opposite way: they ship with no credentials at all and no database. Every figure in them is invented, and the screens that normally read from QuickBooks, Gmail, Drive or the AI review are showing sample responses. That is why they can be handed out freely — there is no connection for them to leak. Changes you make while clicking around are saved in your own browser and nowhere else.
